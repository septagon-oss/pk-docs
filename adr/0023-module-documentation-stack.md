# ADR 0023 — Module documentation is a curated stack, not a single framework

> **Historical proposal — do not implement.** The full PlatformKit
> distribution re-scoped this six-framework proposal in ADR 0053 on
> 2026-06-24 to generated facts plus a short `MODULE.md`; that portfolio ADR is
> not reproduced in this smaller OSS ADR subset. References below to CUE-owned
> module facts or a hand-authored catalog YAML describe an abandoned plan.
> Current catalog authority is [ADR 0048](./0048-go-authored-catalog-and-generated-exports.md).

Status: **Superseded** (2026-06-24) — was **Proposed** (2026-04-25)

## The problem

The workspace ships 46 business modules and produces three kinds of
documentation, none of which capture the things readers actually need
to know.

`<module>/README.md` is generated mechanically by
`cmd/module-docs-generate`. It lists name, archetype, tags, and the
features inside the module. We can read one against today's
`health_management/README.md`:

```
# health_management

Health monitoring and management system

## Metadata
- Archetype: registry
- Category: core
- Base path: /health
- Tags: health, monitoring, core
```

That tells a reader nothing about *why this module exists, what it
intentionally doesn't own, or how it pairs with the four ports it
depends on*. The README is true. It is also useless to anyone trying
to integrate against the module, audit it, or decide whether to keep
it.

`<module>/docs/doc.go` and `<module>/docs/README.md` mirror the same
mechanical metadata into a Go-importable form for tooling. Same
content, second copy.

`.claude/generated/modules/<module>.md` is regenerated by
`platformkit claude sync` to feed Claude. Same content, third copy.

`pk-docs/architecture/` is a workspace-level arc42 with all
twelve sections written narratively. Its §5 Building Block View
describes the workspace topology and the *anatomy* of a module — but
it cannot describe what each of the 46 modules is for, because that's
46 narratives, not one. Today §5 stops at the catalog domain map and
points readers at the catalog yaml.

The result is a documentation system with five surfaces and one job
done. Architects reading the workspace arc42 hit a cliff at §5;
developers integrating a module open a generated README that knows
the module's name and nothing else; agents read the same generated
metadata; auditors find no per-module compliance posture. The cost
shows up every time someone has to ask "what does
`audit_management` actually own and what doesn't it?" — a question
the docs do not answer.

A second-order pain: the workspace already publishes ADRs, ports
catalogs, OpenAPI contracts, AsyncAPI events, PKDS component
contracts, and module manifests. These are excellent. They are also
*disconnected* — no doc surface stitches them into a coherent
per-module view. Each module sits at the centre of seven generated
artifacts that nobody reads together.

A third-order pain: the four audiences have different needs and
nobody serves all four.

- **Architects** want runtime flows, quality requirements, risks,
  cross-module sequence diagrams.
- **Integrators** (other module authors, app composers) want the
  ports the module exposes, the events it emits, how to opt in or
  out of features.
- **Operators** want health, metrics, retention policy, runbook
  pointers, deployment posture.
- **Auditors** want compliance tags, retention, audit emissions,
  decision provenance.

A single generated README cannot serve all four. A single arc42 doc
at workspace scope cannot either — its sections collapse the moment
you try to scope them per module.

Adjacent forces close the decision window now:

- The `cookie_consent` module just shipped. It has the
  same generated stub as every other module and is opaque to anyone
  who didn't write it. It is also a regulatory surface — auditors
  *will* read its docs.
- The catalog has six modules in the consolidation queue (theme →
  admin, job → admin, location/visit → space). Folding them
  without a documented module charter loses the original intent
  silently. A folded module without a charter cannot be unfolded.
- Claude Code, Claude Design, and the agent runtime are
  first-class consumers. Generated metadata is what they ingest.
  The richer the per-module source, the more useful the projection.

## The decision

Adopt a **curated documentation stack** — six frameworks, each owning
the layer it is best at, stitched together by an explicit
single-source-of-truth schema.

We rejected the obvious shape — "pick one framework and apply it
everywhere" — because every framework we surveyed has a strong native
scope and an awkward edge. arc42 is excellent for systems and
strained at building-block scope. Diátaxis is excellent for
user-facing documentation and silent on architectural intent. C4
nails diagrams across scales and is light on prose. ADRs nail
decisions and don't describe state. No single framework covers all
four audiences without being forced.

The stack:

1. **arc42 v8.2** owns the **workspace**. One complete arc42 doc at
   `pk-docs/architecture/` carries the twelve standard
   sections at workspace scope. Already exists; this ADR formalises
   it as the workspace tier and pins the version.
2. **Domain arc42-lite** owns each of the eight domains
   (governance, identity-access, workspace, content-experience,
   engagement, integrations, platform, revenue). Sections §1, §3,
   §4, §5, §6, §11 only — the ones that are meaningful at
   cross-module scope. Domain §5 is the index of modules in that
   domain. Lives at `pk-docs/architecture/domains/<domain>/`.
3. **Module charter** owns each of the 46 modules. Authored in
   **CUE** at `<module>/MODULE.cue` for the facts; **Markdown** at
   `<module>/MODULE.md` for the prose. The Markdown blends three
   frameworks:
   - **Google Design Doc** template ("Goals / Non-goals /
     Considered alternatives / Decision") for the intent section.
     The "Non-goals" and "Considered alternatives" entries make
     boundaries enforceable.
   - **Diátaxis** for the developer-facing body — Tutorial,
     How-to, Reference, Explanation, in that order. Each module's
     reference section transcludes its own OpenAPI / AsyncAPI /
     charter projections; the module author writes only the
     three narrative quadrants.
   - **Module Charter (CUE)** for identity, boundary, surfaces,
     dependencies, operability, references, maturity. Single
     source of truth — the catalog yaml, generated `doc.go`,
     `.claude/generated/modules/`, agent skills, and the Antora
     module page all project from this one CUE file.
4. **C4 + Structurizr DSL** for diagrams at every scale. Each
   module ships `<module>/diagrams/workspace.dsl` (or `.mmd`)
   producing the Container view, Component view, and one or two
   sequence views. Single text source projects to Mermaid for
   inline rendering and to PNG/SVG for the Antora site. Workspace
   and domain docs reuse the same DSL files via Structurizr's
   `extend` directive.
5. **ADRs** (Nygard) unchanged. Already at
   `pk-docs/adr/`. Modules reference ADRs by id; ADRs
   never duplicate per-module narrative.
6. **ISO/IEC 25010** vocabulary for quality attributes inside
   arc42 §10 and the module charter. Eight attributes
   (functional suitability, performance efficiency, compatibility,
   usability, reliability, security, maintainability, portability)
   give a fixed taxonomy so different modules' quality requirements
   are comparable.
7. **DDD ubiquitous language** at workspace level for the
   glossary. Modules cite terms by anchor (`#term-tenant`); they
   do not redefine them.

Three load-bearing scopes, six frameworks, one source of truth per
fact.

The CUE schema (`pk-docs/schemas/module_charter.cue`) is the
contract. Every module's `MODULE.cue` unifies against it at compile
time. The schema captures arc42 fields (goals, constraints, runtime
flows, quality requirements, risks, glossary), charter fields
(identity, boundary, surfaces, dependencies, operability), and
projection metadata (which views to emit, which transclusions to
satisfy).

The narrative `MODULE.md` is human-authored prose with explicit
projection markers (`<!-- @include surfaces -->`,
`<!-- @diagram component -->`). The doc generator fills the projected
blocks; humans own the prose between them. The two never overlap —
prose cannot duplicate facts; facts cannot leak into prose.

## What we gave up

- One-framework simplicity. Authors learn six frameworks by name,
  even if they only touch a small slice of each. Mitigated because
  most are already in use (ADRs, OpenAPI, PKDS) and the per-module
  template is one file, not six.
- A second authoring language (CUE, in addition to Go and
  Markdown) at the module level. Mitigated because CUE is already
  the workspace's design-system authoring language (ADR 0022) and
  the schema is small (~150 lines).
- Time. Roughly two weeks of phased work to land the schema, the
  generator, the projection adapters, the analyzers, and the bulk
  migration of 46 modules to skeletons.
- The illusion that documentation can be fully generated.
  Generators give us facts; humans still have to write intent.
  Eight narrative slots per module (Goals, Non-goals, Considered
  alternatives, Tutorial, How-to×N, Explanation, Risks) require
  domain knowledge. The schema and the generator make those slots
  cheap to fill, not free.

## What we kept

- One source of truth per fact. The catalog yaml, the generated
  `doc.go`, the `.claude/generated/` snapshot, the agent-skill
  manifest, and the Antora module page all project from
  `MODULE.cue`. Drift between them becomes mechanically impossible.
- Composability across scales. Workspace arc42 §5 transcludes
  domain §5; domain §5 transcludes module charter "At a glance".
  Same anchors, three zoom levels, no duplication.
- Audience clarity. Architects open arc42; integrators open the
  module Diátaxis quadrants; operators read the operability and
  health blocks; auditors read the references and operability
  sections — each from their own entry point, all from one source.
- ADRs and PKDS unchanged. Existing investments in those frameworks
  stay; this ADR composes them into a wider system rather than
  replacing them.
- Diagrams as text. Structurizr DSL keeps diagrams diffable,
  reviewable, and reproducible. No more screenshots.
- Enforceability. Five new analyzers (below) keep narrative honest
  and projections current. Drift fails CI, not review.

## How we enforce it

Five analyzers under `cmd/platformkit verify charter`, all run by
`make check-module-charter` in the business-modules repo:

- `charter-exists` — every module in the catalog has both
  `MODULE.cue` and `MODULE.md`. Missing files fail the build.
- `charter-cue-schema` — every `MODULE.cue` unifies against
  `pk-docs/schemas/module_charter.cue`. CUE does this
  natively; the analyzer wraps `cue vet`.
- `charter-surface-parity` — `surfaces.routes` in CUE matches the
  actual `huma.Register` and `apikit.RegisterRawOperation` calls
  in the module's feature handlers; `surfaces.events` matches
  `WithEvent` calls in `events.go`; `surfaces.services` matches
  `b.Service(...)` registrations in feature builders. AST-walked,
  not pattern-matched.
- `charter-dependency-parity` — `dependencies.required` and
  `dependencies.optional` in CUE match the
  `standard.WithDep(module.RequiresPort[T](...))` and
  `standard.WithDep(module.OptionalPort[T](...))` calls in
  `dependencies.go`. The same parity analyzer that today guards
  the catalog yaml extends to the charter.
- `charter-narrative-completeness` — `MODULE.md` has all required
  Diátaxis + Design Doc anchors present, no authoring-placeholder markers, no
  empty `## Goals` / `## Non-goals` / `## Worked example`
  sections. The analyzer runs only after `charter-cue-schema`
  passes — no narrative is checked against a broken charter.

Two further analyzers at workspace scope:

- `arc42-anchor-stability` — every workspace and domain arc42
  section has a stable anchor (`{#sec-5}`); transclusion targets
  resolve. Catches accidental section renumbering.
- `charter-references-resolve` — every cited ADR file exists,
  every cited related module is in the catalog, every cited
  external standard URL is in the allowlist
  (`pk-docs/architecture/external-references.yaml`).

Existing analyzers are kept and become part of the same gate:

- `check-module-contracts` — the catalog conformance suite that
  already validates `module_contracts.yaml`. It will start
  cross-checking the catalog yaml against `MODULE.cue`.
- `check-module-doc-contract` — the existing per-module docs
  contract check. It will be retired once the charter projections
  cover its surface area.

## Migration phases

Each phase has a binary exit criterion and is independently mergeable.

1. **Phase 0 — ADR + schema + worked example (this slice).**
   Land this ADR. Land
   `pk-docs/schemas/module_charter.cue`. Land
   `pk-docs/templates/MODULE.cue.tmpl` and
   `MODULE.md.tmpl`. Author
   `cookie_consent/MODULE.cue` and `MODULE.md` fully —
   the worked example. Land
   `pk-docs/architecture/domains/governance/arc42.md` as
   the first domain doc, transcluding the cookie_consent module
   charter. Exit: one module fully documented end-to-end under
   the new stack; schema validates.
2. **Phase 1 — Generator and projections.** Build
   `cmd/platformkit charter` (subcommands: `init`, `project`,
   `check`). The `project` subcommand reproduces the existing
   generated outputs (`docs/doc.go`, `docs/README.md`,
   `.claude/generated/modules/<m>.md`, the catalog yaml entry,
   the agent-skill manifest) from `MODULE.cue`. Exit:
   `cookie_consent`'s generated outputs are produced
   by the new generator and are byte-identical (or
   intentionally-improved) to the current outputs.
3. **Phase 2 — Analyzers.** Build the five charter analyzers and
   wire them into the business-modules `precommit` target. Exit:
   `make check-module-charter` runs and passes for
   `cookie_consent`.
4. **Phase 3 — Bulk skeleton migration.** Run
   `platformkit charter init` against every module to generate a
   skeleton `MODULE.cue` from existing metadata
   (`module.go` constants, `dependencies.go` ports, feature
   listings, event declarations). Generate skeleton `MODULE.md`
   with narrative slots marked `<!-- authoring-placeholder -->`. Exit:
   46 charter pairs exist; `cue vet` passes on all 46;
   `charter-narrative-completeness` reports the open authoring placeholders as
   warnings, not errors, until Phase 5.
5. **Phase 4 — Domain docs.** Author the eight domain
   `arc42.md` files. Each transcludes the modules in its domain
   via the §5 anchor. Exit: workspace arc42 §5 transcludes the
   eight domain docs; every module is reachable two clicks down.
6. **Phase 5 — Narrative fill.** Domain owners write the
   narrative slots for the modules in their domain. Per-module
   work is bounded — eight slots, none longer than two
   paragraphs. The `charter-narrative-completeness` analyzer
   becomes an error-level gate at the end of this phase.
7. **Phase 6 — Consolidate generated docs.** Delete the superseded
   `cmd/module-docs-generate`, `cmd/module-docs-contract-check`,
   `<module>/README.md` (the generated stub),
   `<module>/docs/{doc.go,README.md}`. The charter generator
   produces equivalents. Exit: superseded doc surfaces removed; the
   six-framework stack is the only surface.

## Alternatives we rejected

- **Full arc42 per module.** Attractive — one framework,
  twelve sections, recognised standard. Rejected because most
  arc42 sections collapse at module scope. A module's
  "Deployment View" reduces to `tier + presets`. A module's
  "Solution Strategy" is one paragraph that could fit anywhere.
  46 × 12 = 552 anchors, most thin or empty. The framework
  becomes ceremony.
- **Diátaxis-only.** Attractive — Django and Cloudflare prove
  it scales. Rejected because Diátaxis is silent on
  architectural intent. There is no place in Diátaxis for
  "what is the boundary of this module against
  `audit_management`". Diátaxis is the right shape for the
  developer-facing *body* of module docs, not the whole.
- **Backstage TechDocs.** Attractive — Spotify uses it at
  scale; the catalog model is genuinely good. Rejected because
  it's opinionated about MkDocs and we already have Antora;
  the catalog model is what we want, and we already have a
  better one. Borrowing its catalog *concepts* is fine;
  adopting its toolchain is not.
- **Hand-written per-module prose, no schema.** Attractive —
  zero new tooling. Rejected because every existing
  generator (catalog yaml, doc.go, .claude/, agent skills)
  needs the same facts. Without a single source those facts
  drift. We have already lived this — see ADR 0022 for the
  three-source-of-truth design-system pipeline that produced
  shipped defects.
- **arc42 + Diátaxis with no charter.** Closer to right.
  Rejected because the projection problem remains — every
  consumer of module metadata still needs the same facts in
  the same shape, and without a typed source those facts are
  re-derived in every projection. The CUE charter is the same
  move PKDS made for design tokens (ADR 0022); the same
  reasoning applies.
